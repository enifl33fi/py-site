# P4. Развёртывание на Helios с контролем качества доставки

## Цель

Автоматизировать публикацию статического сайта на Helios ИТМО
по SSH/rsync с отдельным deploy-ключом, добавить healthcheck,
preview-сборки для PR и механизм отката.

## Архитектура

### Репозиторий

- GitHub: <https://github.com/enifl33fi/py-site>
- Основная ветка: `master`
- Генератор: MkDocs + Material

### Цели публикации

| Цель | Хостинг | Триггер | Метод доставки |
|---|---|---|---|
| Прод | GitHub Pages | push в `master` | `upload-pages-artifact` + `deploy-pages` |
| Прод | Helios ИТМО | push в `master` | SSH/rsync + переключение симлинка |
| Превью | Helios ИТМО | PR в `master` | SSH/rsync в `preview/pr-<N>/` |
| Очистка | Helios ИТМО | закрытие PR | SSH `rm -rf` |

### Workflow-файлы

- `.github/workflows/_build.yml` — reusable: `lint`, `build-github`, `build-helios`
- `.github/workflows/prod.yml` — на push в `master`
- `.github/workflows/preview.yml` — на `pull_request` (opened/synchronize/reopened)
- `.github/workflows/cleanup.yml` — на `pull_request` (closed)

### Схема

    push в master ──► prod.yml ──► lint ──► build-github ──► deploy-pages
                                       └──► build-helios ──► deploy-helios-prod

    PR в master ───► preview.yml ─► lint ──► build-* ─────► deploy-helios-preview

    PR closed ─────► cleanup.yml ────────────────────────► cleanup-helios-preview

## Структура каталогов на Helios

    $HELIOS_PATH/
    ├── releases/
    │   ├── 20251005120000/   # каждый деплой — отдельный каталог
    │   └── 20251005121500/
    ├── preview/
    │   └── pr-42/            # превью по номеру PR
    └── current -> releases/20251005121500   # симлинк на активный релиз

Веб-сервер настроен отдавать статику из `current` (Apache + `FollowSymLinks`).
Новый релиз сначала полностью заливается в `releases/<TS>/`, и только потом
симлинк `current` переключается на него.

Симлинк заменяется командой

    rm -f current && ln -s releases/<TS> current

Это не строго атомарная операция: между `rm` и `ln` симлинка нет несколько
миллисекунд. Изначально предполагался атомарный вариант через `mv -T`
(`rename(2)`, GNU coreutils), но Helios работает на FreeBSD, где `-T`
недоступен — см. «Ошибка 5». Для статического сайта под низкой нагрузкой
окно в несколько миллисекунд не имеет значения.

## Безопасность

- Отдельный deploy-ключ `py_site_deploy`, не пересекается с личным `id_rsa`.
- Публичная часть добавлена в `~/.ssh/authorized_keys` на Helios.
- Приватная часть хранится только в GitHub Secrets (`HELIOS_SSH_KEY`).
- `known_hosts` зафиксирован в секрете `HELIOS_KNOWN_HOSTS`, `StrictHostKeyChecking` **не отключён**.
- Превью и очистка выполняются только для PR из этого же репозитория:

      github.event.pull_request.head.repo.full_name == github.repository

  Это защищает от утечки секретов через PR из форков.

## Healthcheck

После деплоя job проверяет:

1. `GET $HELIOS_URL/health.txt` возвращает HTTP 200.
2. В теле ответа есть контрольная строка `P4_DEPLOY_OK py-site`.

Если любое из условий нарушено — job завершается с ошибкой.
Это гарантирует, что «зелёный» прогон означает реально доступный сайт,
а не просто успешно выполненный rsync.

## Preview-сборки

Каждый PR в `master` публикуется в отдельный подкаталог:

    https://se.ifmo.ru/~s367380/py-site/preview/pr-<N>/

Имя каталога = номер PR, а не имя ветки. Это стабильно:
переименование ветки не ломает URL превью, а закрытие PR однозначно
определяет, что удалять.

При новом коммите в PR `rsync --delete` обновляет содержимое `pr-<N>/`.
При закрытии PR job `cleanup` делает `rm -rf preview/pr-<N>/`. Прод-каталог
`releases/` при этом не трогается.

## Откат

Так как каждый деплой сохраняется в `releases/<TS>`, откат — это переключение
симлинка на предыдущий релиз:

    ssh -i ~/.ssh/py_site_deploy -p 2222 s367380@se.ifmo.ru \
      "rm -f '$HELIOS_PATH/current' && \
       ln -s '$HELIOS_PATH/releases/<TS_предыдущего>' '$HELIOS_PATH/current'"

Пересборка не нужна, файлы предыдущего релиза уже лежат на сервере.
Откат занимает доли секунды.

## Сравнение GitHub Pages и Helios

| Критерий | GitHub Pages | Helios |
|---|---|---|
| Время доставки | 1–3 мин | 30–90 с |
| Надёжность | высокая, SLA | зависит от сервера |
| HTTPS | из коробки | из коробки |
| Свой домен | поддерживается | ограниченно |
| Удобство отладки | логи Actions | логи Actions + SSH вручную |
| Откат | через артефакт предыдущего run | symlink на `releases/<TS>` |
| Preview | нет подкаталогов | `preview/pr-<N>/` |
| Поведение при обрыве деплоя | атомарное переключение на стороне GitHub | `rsync` идёт в `releases/`, прод не тронут до переключения симлинка; само переключение — `rm -f && ln -s`, окно ~мс |

## Отладка

### Ошибка 1. `mkdocs build --strict` падает на битой ссылке

**Текст:**

    ERROR - Doc file 't1.md' contains a link 'no-such.md',
    but the target 'no-such.md' is not found among documentation files.

**Гипотеза:** относительный путь указан не от текущего файла.

**Проверка:** `mkdocs build -f mkdocs.github.yml --strict -v`.

**Решение:** заменил ссылку на корректный относительный путь.

### Ошибка 2. `Host key verification failed` в CI

**Текст:**

    Host key verification failed.
    rsync: connection unexpectedly closed

**Гипотеза:** в раннере нет `known_hosts` для `[se.ifmo.ru]:2222`.

**Проверка:** локально `ssh -o UserKnownHostsFile=~/.ssh/py_site_known_hosts -p 2222 ...`.

**Решение:** снял ключ сервера через `ssh-keyscan -p 2222 -H se.ifmo.ru`,
положил в секрет `HELIOS_KNOWN_HOSTS`, в workflow записал в `~/.ssh/known_hosts`.
`StrictHostKeyChecking` не отключал.

### Ошибка 3. Секреты не передаются в PR из форка

**Текст:**

    Permission denied (publickey).
    rsync error: unexplained error (code 255)

**Гипотеза:** GitHub не отдаёт секреты для `pull_request` из форков.

**Проверка:** посмотрел в логе, что `HELIOS_SSH_KEY` пустой.

**Решение:** добавил в превью-джобу и cleanup-джобу условие

    if: github.event.pull_request.head.repo.full_name == github.repository

Для PR из форков превью просто не создаётся, прод не трогается.

### Ошибка 4. Сайт открывается, но ссылки ведут на GitHub Pages

**Текст:** визуально — клик по пункту меню ведёт на чужой домен.

**Гипотеза:** в `mkdocs.helios.yml` остался `site_url` от GitHub Pages.

**Проверка:** `grep -o 'https://[^"]*' site/index.html | head`.

**Решение:** в `mkdocs.helios.yml` установил

    site_url: https://se.ifmo.ru/~s367380/py-site/

С завершающим слэшем. Пересобрал — ссылки корректны.

### Ошибка 5. `mv: illegal option -- T` на FreeBSD

**Текст:**

    mv: illegal option -- T
    usage: mv [-f | -i | -n] [-hv] source target
    Error: Process completed with exit code 64.

**Гипотеза:** Helios работает на FreeBSD, где `mv` — BSD-версия, а не GNU coreutils. Флаг `-T` (no-target-directory), использовавшийся для атомарной замены симлинка, — расширение GNU, в BSD его нет.

**Проверка:**

    ssh -p 2222 s367380@se.ifmo.ru "uname -a"
    # FreeBSD se.ifmo.ru ...

    ssh -p 2222 s367380@se.ifmo.ru "mv --version 2>&1 | head -1"
    # mv: unknown option -- version

**Решение:** отказался от `ln -sfn ... current-next && mv -T ... current`.
Итоговая команда портируема и на GNU, и на BSD, и на busybox:

    rm -f '$BASE/current' && ln -s '$BASE/releases/$TS' '$BASE/current'

Атомарность `rename(2)` теряется: между `rm` и `ln` симлинка нет несколько
миллисекунд. Для статического сайта под низкой нагрузкой это несущественно.

## Вывод

Рекомендуемый стек для публикации результатов исследований:

- **Генератор:** MkDocs + Material;
- **CI/CD:** GitHub Actions с reusable workflow и разделением на prod/preview/cleanup;
- **Хостинги:** GitHub Pages (прод) + Helios ИТМО (прод + превью + откат);
- **Доставка:** SSH/rsync с отдельным deploy-ключом, `known_hosts` зафиксирован;
- **Контроль качества:** `mkdocs build --strict` + healthcheck по HTTP 200 и контрольной строке.

Ограничения, при которых рекомендация меняется:

- тяжёлые вычисления на этапе сборки → выносить из CI, публиковать готовые артефакты;
- autodoc из Python-кода → Sphinx + MyST;
- основа — Jupyter-ноутбуки → Quarto;
- нужен S3-совместимый хостинг → заменить rsync на S3 API.
